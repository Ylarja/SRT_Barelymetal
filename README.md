# CAN Bus Analyzer 

This repository contains the step-by-step guide to reproduce our CAN bus analyzer: a **HALO** network (Arduino Portenta H7 controller + Adafruit responders) monitored by a **Listener** node running on PetaLinux on a Xilinx Zynq® UltraScale+™ MPSoC ZCU104, using only the Processing System (PS).

## 1. Hardware Design (Vivado)

### 1.1 Create the Project and the Block Design

1. **Create Project** → **RTL Project** (tick *Do not specify sources at this time*) → in **Boards** select **Zynq UltraScale+ ZCU104 Evaluation Board** → **Finish**.
2. **Create Block Design** → **+** → add **Zynq UltraScale+ MPSoC**.
3. Click **Run Block Automation** (keep *Apply Board Preset* ticked) → **OK**.

### 1.2 Configure the PS

Double-click the Zynq block (**Customize Block**):

- **PS-PL Configuration → PS-PL Interfaces → Master Interface**: untick **AXI HPM0 FPD** and **AXI HPM1 FPD**. We use only the PS, so we do not need PS↔PL communication.
- **I/O Configuration → Low Speed → I/O Peripherals**:
  - enable **CAN 1** on **MIO 24..25**
  - keep **UART** enabled (serial console)
- **I/O Configuration → Low Speed → Memory Interfaces**: keep **SD** enabled (boot from micro-SD)

> 📷 **[SCREENSHOT: Zynq UltraScale+ PS configuration – CAN1 on MIO 24..25, UART, SD]**

### 1.3 Validate, Generate and Export

1. **Validate Design** (F6).
2. In *Sources*, right-click `design_1` → **Create HDL Wrapper** → *Let Vivado manage wrapper and auto-update*.
3. **Generate Block Design** → *Global* → **Generate**.
4. **Generate Bitstream**.
5. **File → Export → Export Hardware** → *Include bitstream* → name `design_1_wrapper` → **Finish**.

> 📷 **[SCREENSHOT: final block design / configuration generated by Vivado]**

The resulting `design_1_wrapper.xsa` is in `vivado/` in this repository.

## 2. Host Environment Setup (Ubuntu)

### 2.1 Install the Dependencies

```bash
sudo apt-get update
sudo apt-get install -y gawk gcc git make net-tools libncurses5-dev zlib1g-dev \
  libssl-dev flex bison libselinux1 gnupg diffstat chrpath socat xterm autoconf \
  libtool texinfo gcc-multilib build-essential libsdl1.2-dev libglib2.0-dev \
  lsb-release scdoc valgrind
```

### 2.2 Switch `/bin/sh` from dash to bash

The PetaLinux (Yocto/bitbake) scripts require `/bin/sh` to be bash:

```bash
sudo ln -sf bash /bin/sh
ls -l /bin/sh      # should print: /bin/sh -> bash
```

### 2.3 Install PetaLinux 2023.2

```bash
mkdir -p ~/petalinux/2023.2
cd ~/Downloads
chmod +x petalinux-v2023.2*-installer.run
./petalinux-v2023.2*-installer.run --dir ~/petalinux/2023.2
```

> ⚠️ **Warning:** run the installer as a normal user, **not** with `sudo`.

Set up the environment (in every new terminal) and check it:

```bash
source ~/petalinux/2023.2/settings.sh
echo $PETALINUX    # should print /home/<your_user>/petalinux/2023.2
```

## 3. PetaLinux Project

### 3.1 Create the Project

We do **not** use the ZCU104 BSP. We start from the generic `zynqMP` template, so the device tree is generated only from the hardware we designed in Vivado:

```bash
cd ~
petalinux-create -t project --template zynqMP -n can_analyzer_os
cd can_analyzer_os
```

### 3.2 Import the Hardware

Point PetaLinux to the folder that contains the `.xsa`:

```bash
petalinux-config --get-hw-description=<PATH_TO_XSA_FOLDER>
```

The configuration menu opens. Press **Exit** and **Save** for now.

### 3.3 Save Disk Space (`rm_work`)

This setting deletes the intermediate build files of each package once it has been built:

```bash
echo 'INHERIT += "rm_work"' >> project-spec/meta-user/conf/petalinuxbsp.conf
tail -n 2 project-spec/meta-user/conf/petalinuxbsp.conf
```

### 3.4 Root Filesystem on micro-SD (EXT4)

By default the rootfs is loaded into RAM (INITRAMFS) and is lost at every power-off. We need persistent logs, so the rootfs goes on the SD card:

```bash
petalinux-config
```

**Image Packaging Configuration**:
- **Root filesystem type** → `EXT4 (SD/eMMC/SATA/USB)`
- **Device node of SD device** → `/dev/mmcblk0p2`

**Save** → **Exit**.

### 3.5 Kernel: SocketCAN

```bash
petalinux-config -c kernel
```

Enable as **built-in** `[*]` (press `/` to search for a symbol):

| Option | Kconfig symbol | Why |
|---|---|---|
| CAN bus subsystem support | `CONFIG_CAN` | CAN as a network interface (SocketCAN) |
| Raw CAN Protocol | `CONFIG_CAN_RAW` | read raw frames (ID + payload) |
| Broadcast Manager CAN Protocol | `CONFIG_CAN_BCM` | handle timeouts deterministically |
| Xilinx CAN | `CONFIG_CAN_XILINXCAN` | driver for the Zynq CAN controller |

> 📷 **[SCREENSHOT: kernel configuration – CAN options]**

### 3.6 Root Filesystem Packages: `iproute2` and `can-utils`

```bash
petalinux-config -c rootfs
```

Enable **`iproute2`** (to bring up `can0`) and **`can-utils`** (`candump`, `cansend`), which we use to test the wiring and the controller before running our own software. Check that both are enabled:

```bash
grep -E "CONFIG_can-utils|CONFIG_iproute2" project-spec/configs/rootfs_config
# CONFIG_can-utils=y
# CONFIG_iproute2=y
```

### 3.7 Device Tree Override

The generated device tree leaves the CAN controller disabled. Build the device tree, then find the CAN node:

```bash
petalinux-build -c device-tree
grep -rn "can@" components/plnx_workspace/device-tree/device-tree/
# look for can@ff070000 (CAN1)
```

Force it on in `system-user.dtsi`:

```bash
nano project-spec/meta-user/recipes-bsp/device-tree/files/system-user.dtsi
```

```dts
/include/ "system-conf.dtsi"
/ {
};

&can1 {
    status = "okay";
};
```

The full file is in `petalinux/system-user.dtsi` in this repository.

## 4. Build and Deploy on the micro-SD

### 4.1 Build

```bash
petalinux-build
```

This takes a long time on the first run.

### 4.2 Generate `BOOT.BIN` (without bitstream)

Our design uses only the PS, so we leave the PL bitstream out of `BOOT.BIN` (no `--fpga`). The board boots faster this way:

```bash
petalinux-package --boot --u-boot --force
ls -l images/linux/    # BOOT.BIN, image.ub, boot.scr, rootfs.tar.gz
```

> 📷 **[SCREENSHOT: system build output]**

### 4.3 Partition the micro-SD

```bash
sudo apt install -y gparted dosfstools mtools
lsblk                  # identify the SD card (e.g. /dev/mmcblk0)
sudo gparted
```

Create the following layout:

| # | Size | Filesystem | Label | Content |
|---|---|---|---|---|
| 1 | 512 MB | FAT32 | `BOOT` | `BOOT.BIN`, `image.ub`, `boot.scr` |
| 2 | remaining space | EXT4 | `rootfs` | root filesystem |

> 📷 **[SCREENSHOT: SD card partitioning in GParted]**

> ⚠️ **Warning:** double-check the device in `lsblk` before applying. GParted erases the selected disk.

### 4.4 Copy the Files to the SD

Remove and reinsert the SD so that Ubuntu mounts it under `/media/$USER/`, then copy the files:

```bash
cd ~/can_analyzer_os
cp images/linux/BOOT.BIN /media/$USER/BOOT/
cp images/linux/image.ub /media/$USER/BOOT/
cp images/linux/boot.scr /media/$USER/BOOT/
sudo tar xvf images/linux/rootfs.tar.gz -C /media/$USER/rootfs
```

Run `sudo` so that `tar` keeps the file ownership and permissions. Then flush the data and unmount:

```bash
sync
sudo umount /media/$USER/BOOT /media/$USER/rootfs
```

> ⚠️ **Warning:** do not skip `sync`. Removing the card before pending writes are flushed corrupts the filesystem and leads to a kernel panic at first boot.
